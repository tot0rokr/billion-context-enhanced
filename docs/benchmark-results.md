# 벤치마크 결과와 평가

A는 기본 Codex, B는 원본 billion-context, C는 이 저장소에 보관한 개선판이다. 세 조건 모두 숨김 기능 검사 13/13과 도구 없는 기억 검사 48/48을 통과했다. C의 관측 시간, 총 입력, 출력 토큰은 B보다 작았지만, 날짜가 다른 단일 실행이므로 패치 효과의 통계적 증거는 아니다.

측정 방법은 [벤치마크 방법](benchmark-methodology.md), 기계가 읽는 원본 집계는 [comparison-ABC.json](../benchmarks/results/comparison-ABC.json), 비용 가정과 정확한 금액은 [cost-estimate.json](../benchmarks/results/cost-estimate.json)에 있다.

토큰은 메인과 서브에이전트 전체의 누적량이다. 과거 대화를 여러 요청에 다시 넣은 양도 포함하므로 동시 컨텍스트 크기와 같지 않다. cached input과 reasoning output은 각각 input과 output 안에 이미 들어 있다.

C의 총 입력 감소와 별개로 uncached input은 B보다 증가했다. 따라서 “토큰이 몇 퍼센트 줄었으니 비용도 같은 비율로 줄었다”고 계산할 수 없다. 평균 속도, 신뢰구간, 반복 성공률은 조건별 한 번으로 추정하지 않았다.

## 비용 환산

이 실험은 Codex 구독으로 실행했다. 아래 금액은 2026-11-13에 확인한 공개 Standard API 단가를 보고된 usage에 적용한 환산값이다. 구독의 실제 청구액, 추가 결제액 또는 포함 사용량 차감량이 아니다.

| 100만 토큰당 USD | 단가  |
| ---------------- | ----- |
| uncached input   | 10.00 |
| cached input     | 1.00  |
| cache write      | 12.50 |
| output           | 50.00 |

요청의 input이 272,000토큰을 초과하면 해당 요청 전체의 input, cache 단가에 2배, output 단가에 1.5배를 적용했다. 초과분에만 할증한 것이 아니다. 근거는 [GPT-6 Astra 모델 문서](https://developers.openai.com/api/docs/models/gpt-6-astra), [prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching), [reasoning](https://developers.openai.com/api/docs/guides/reasoning), [구독 가격 문서](https://learn.chatgpt.com/docs/pricing)다. 단가가 바뀌어도 역사 비교의 가정은 위 값으로 보존한다.

요청별 input을 `I`, cached input을 `C`, cache-write input을 `W`, output을 `O`라 하면 계산식은 다음과 같다. `C`와 `W`는 서로 겹치지 않는 input 범주로 취급한다.

```text
U = I - C - W
input_multiplier = 2   if I > 272000 else 1
output_multiplier = 1.5 if I > 272000 else 1
USD = (input_multiplier * (10 * U + 1 * C + 12.5 * W)
       + output_multiplier * 50 * O) / 1000000
```

| USD 구성               | A: 기본 Codex | B: 원본   | C: 개선판 |
| ---------------------- | ------------- | --------- | --------- |
| uncached input         | 7.970930      | 8.552880  | 9.707770  |
| cached input           | 27.414144     | 12.943488 | 10.893952 |
| cache write            | 0.000000      | 0.000000  | 0.000000  |
| output                 | 6.778325      | 5.938200  | 4.644450  |
| 합계                   | 42.163399     | 27.434568 | 25.246172 |
| 긴 입력 할증 대상 요청 | 27            | 0         | 0         |

A는 긴 입력 할증이 없다고 가정하면 $31.125468이며, 적용한 할증은 $11.037931이다. C는 이 환산에서 B보다 약 7.98%, A보다 약 40.12% 작다. 실제 구독 한도를 같은 비율로 절약했다는 뜻은 아니다.

- reasoning 토큰은 output에 이미 포함되어 별도 청구 항목을 더하지 않았다.
- 관측된 cache-write 토큰은 모두 0이다. 일반 input과 cache-write 단가를 같은 토큰에 중복 적용하지 않았다.
- Fast, Flex, Batch, 지역, 세금, 계약별 배율은 적용하지 않았다. 로컬 Docker와 셸을 OpenAI hosted tool 사용료로 계산하지 않았다.
- B/C의 내부 컨텍스트 관리 응답 비용은 각각 $4.815538, $4.223524이며 합계에 이미 포함됐다.
- A에는 output이 0인 응답 20개가 보고한 input 191,392토큰이 있다. 보고량대로 포함했다. 이를 전부 무료라고 가정한 민감도 값은 $40.249479이나, 무료라는 증거는 아니다.
- B/C에서 usage 없이 취소된 요청의 비용은 미상이다. 제외된 사용량 때문에 API 환산도 완전한 청구 재구성은 아니다.

## 압축 동작과 수정 경로

| 항목                    | A: 기본 Codex | B: 원본   | C: 개선판 |
| ----------------------- | ------------- | --------- | --------- |
| 성공한 compress 호출    | 해당 없음     | 5         | 3         |
| 생성된 T1 block         | 해당 없음     | 8         | 5         |
| 무효 압축               | 해당 없음     | 7         | 4         |
| 컨텍스트 관리 모델 응답 | 0             | 25        | 15        |
| 그 응답의 input         | 0             | 2,922,764 | 2,081,565 |
| 그 응답의 output        | 0             | 18,661    | 11,177    |

무효 압축은 호출이 끝났지만 새 압축 block이 0개인 경우다. 보호된 범위나 이미 처리된 범위를 요약하려 하면 발생할 수 있다. 새 block이 없어도 모델이 범위를 고르고 요약을 작성한 비용은 발생할 수 있다.

C의 무효 압축 receipt 경로는 실제 비교에서 4회 실행됐다. 메시지별 상태 표시 개선은 이 실행에서 호출되지 않았다. 사용한 uncompressed status report 7개는 기존 range 표시였다. 따라서 C의 모든 수정이 측정된 시간 차이에 기여했다고 주장하지 않는다.

C는 무효 압축 때 상태 재계산을 생략하고, marker가 활성화된 streaming Responses의 무효 압축만 있는 round에서 client-visible receipt를 사용한다. 모델 재시도의 강제 상한을 추가한 것이 아니며, 요청 사이 cache prefix 보존 효과도 확립하지 않았다. Anthropic 등 다른 wire의 도구 결과 전달 방식은 유지한다.

## 구현 과정의 보조 지표

| 지표                           | A: 기본 Codex | B: 원본 | C: 개선판 |
| ------------------------------ | ------------- | ------- | --------- |
| 초기 단계 첫 메인 전체 테스트  | 25/25         | 26/26   | 20/20     |
| 최종 단계 자체 테스트          | 68/68         | 57/57   | 39/39     |
| 메인 셸 명령 실패              | 7             | 6       | 3         |
| 그중 환경, 명령 문제           | 4             | 5       | 3         |
| 그중 아직 없는 파일 읽기       | 3             | 1       | 0         |
| 전체 agent의 exec_command 호출 | 143           | 132     | 136       |
| 전체 agent의 apply_patch 호출  | 42            | 29      | 27        |
| 전체 agent의 send_message 호출 | 40            | 41      | 30        |
| 최상위 구현 Python 파일 수     | 4             | 4       | 4         |
| 해당 구현 파일의 물리적 줄 수  | 546           | 479     | 434       |

호출 수는 thread와 call ID를 기준으로 집계한다. 줄 수에는 주석, 빈 줄이 포함되고 테스트 파일은 제외한다. 실제 후보 파일과 arm별 실행, metrics 기록을 근거로 한 관측값이다.

초기 통합 테스트는 각 후보가 직접 만든 서로 다른 테스트이며, 서브에이전트가 그 전에 수정했을 수 있다. 첫 제출의 공통 숨김 테스트 통과율과 같지 않다. 테스트 수가 많다고 검증력이 높다는 결론도 내리지 않는다.

명령 실패는 `rg`, `python` 부재, Git 저장소가 아닌 곳의 `git status`, 다른 agent가 아직 만들지 않은 파일 읽기 등이다. 생성한 프로그램의 버그 수로 계산하지 않는다. `apply_patch`에는 구현, 요구사항 변경, 테스트, 문서 작성이 모두 포함되므로 재작업 횟수나 결함 수정 횟수로 해석하지 않는다.

정확한 최초 구현 성공률, 고유 결함 수, 요구사항이 유지된 기능의 회귀 수, 결함별 수정 비용은 수집하지 않았다. 초기, 중간 소스 스냅샷과 공통 검사 기록이 없고 서브에이전트 도구 출력 본문도 telemetry에서 생략돼 소급 확정할 수 없다.

## 해석의 한계와 후속 평가

- 세 조건은 각각 한 번 실행했고 C의 실행일이 다르다. 서버 부하, 모델 제공 상태, 에이전트 구현 전략의 영향을 분리하지 못한다.
- 최대 실제 입력은 A 약 38만, B/C 약 19만 토큰이다. effective window 828,400을 소진하는 극단 상황까지 밀어붙이지 않았다.
- 관측 block은 T1이다. 여러 계층의 장기 재압축, 장기간 세션, 수억, 수십억 토큰 처리 품질은 검증하지 않았다.
- 48개 기억 항목은 보존하라고 명시했고 전부 맞았다. 임의 세부사항의 완전 보존 또는 검색 품질을 입증하지 않는다.
- 원문 보존과 모델의 회수 능력은 별개다. 원문 파일 공개 후 정답을 맞힌 것을 압축 검색의 성공으로 계산하지 않는다.
- Claude의 성능, 비용, 구독 E2E는 측정하지 않았다. 이 비교를 Claude 결과로 일반화하지 않는다.
- 여러 독립 과제, seed, 실행 순서의 반복, 첫 제출 외부 채점, 단계별 snapshot, mutation testing을 추가하면 완성 품질과 수정 비용을 더 구별할 수 있다. 이들은 후속 평가 제안이며 현재 결과가 아니다.
